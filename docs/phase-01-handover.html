1이 프로젝트가 뭐야

3분 안에 핵심 잡기.

logos-rag 는 사용자가 한국어로 성경에 대해 질문하면, 영문 성경에서 의미적으로 가까운 구절을 찾아서 한국어 답변을 만들어주는 풀스택 RAG 앱이에요.

예시:

사용자 → "하나님이 세상을 만든 이야기 알려줘"

   ↓ (검색)

영문 verse → "In the beginning God created the heavens and the earth." (Gen 1:1)

   ↓ (LLM 답변)

답변 → "성경의 첫 절은 창세기 1장 1절로, 하나님이 천지를 창조하신 것을
       선언합니다. ..." + 영문 근거 verse 표시

v1 의 4단계 phase 중 phase-01 (데이터 파이프라인) 이 이 문서의 범위. 이게 끝나야 LLM·UI·인증·배포로 갈 수 있어요.

왜 RAG?

LLM 한테 "성경 뭐가 있어?" 물으면 환각(hallucination) 위험 ↑. 대신 진짜 성경 텍스트를 DB 에서 찾아 LLM 에게 "이 구절들 보고 답해" 라고 주면 정확도 ↑. 이게 RAG (Retrieval-Augmented Generation).

왜 임베딩?

"하나님이 세상을 만든" 같은 한국어 표현으로 영문 성경 DB 를 검색하려면 키워드 매칭 (LIKE) 으로 안 됨. 의미를 좌표(벡터)로 만들어서 가까운 좌표를 찾는 방식이 필요 → 임베딩.

5각 spec 이 왜 있는지 — 스토리

단순 산출물 나열이 아니라, 왜 이 순서로 만들어졌나.

spec-01-01 Supabase 부트스트랩 Merged

Supabase 프로젝트와 연결되는 통로 만들기

왜 첫 spec? — 어떤 작업이든 DB 와 연결 안 되면 시작 못 함. 그래서 가장 먼저 "pnpm check:supabase 한 줄로 연결 잘 됐는지 확인" 가능한 상태를 만들었어.

핵심 결정: Supabase JS (앱 코드용) + pg 직접 연결 (셋업·검증·배치용) 두 통로 동시 사용. 같은 DB 지만 가는 길이 다름.

발견: Supabase 신규 키 형식 (sb_publishable_*/sb_secret_*) 이 표준. 2026년 말 legacy JWT 키 제거 예정.

spec-01-02 WEB 성경 fetch + 정규화 Merged

외부 출처에서 영문 성경을 받아 평면 JSON 으로 정리

왜? — 검색하려면 일단 데이터가 있어야 함. 3개 출처 후보 비교 후 gratis-bible/bible (OSIS XML) 선택. 6.6MB 짜리 JSON 한 파일에 31,102 verse 모두 정규화.

핵심 결정: 결정성 보장 (같은 출처 → byte-identical JSON). repo 에 commit 해서 clone 즉시 사용 가능.

발견: WEB(World English Bible) 이 KJV 보다 현대 영어라 임베딩 모델 친화적. 둘 다 public domain.

spec-01-03 verses 테이블 + Supabase CLI Merged

데이터가 들어갈 그릇 (스키마) 정의

왜? — JSON 만 있고 DB 에 비어있으면 검색 못 함. verses 테이블 만들 때 그냥 Dashboard 에서 클릭하면 다음에 못 재현 → Supabase CLI 도입해서 SQL 마이그레이션 파일로 버전 관리.

스키마:

CREATE TABLE verses (
  id        BIGSERIAL PRIMARY KEY,
  book      TEXT NOT NULL,
  chapter   INTEGER NOT NULL,
  verse     INTEGER NOT NULL,
  text      TEXT NOT NULL,
  embedding extensions.vector(768),  -- 다음 spec 에서 채움
  UNIQUE (book, chapter, verse)
);
ALTER TABLE verses ENABLE ROW LEVEL SECURITY;  -- 정책 0개 = secret key 만

발견: Supabase 는 pgvector 를 extensions 스키마에 둠 → extensions.vector(768) 으로 schema-qualified 강제. SET search_path 도 필요한 경우 있음.

spec-01-04 임베딩 적재 (2-pass) Merged

JSON → DB · text → 768d 벡터로 변환

왜 2-pass? — 한 번에 다 하면 (1-pass) 중간 실패 시 "어디까지 했지?" 가 흐려짐. 1pass(31k text 한 번에 INSERT) → 2pass(NULL embedding 만 골라 Gemini 호출 → UPDATE) 분리하면 DB 자체가 진행의 진실의 출처. 재실행 시 WHERE embedding IS NULL 한 줄로 이어 적재.

모델: gemini-embedding-001 + outputDimensionality:768

발견 3개: (1) 원래 모델 text-embedding-004 가 2026-01-14 deprecated → 마이그레이션 (2) Gemini batch API 의 N contents 가 N requests 로 카운트됨 (실측) (3) 무료 tier 일일 1,000 requests 한도. 그래서 현재 1,000 / 31,102 적재 상태로 spec scope 축소.

spec-01-05 cosine 검색 + 평가 Merged

진짜로 의미 검색이 되는지 함수 정의 + 측정

왜? — embedding 컬럼이 채워져도 그냥 숫자 덩어리. 거기서 의미 가까운 row 를 꺼내는 함수가 있어야 진짜 검색. match_verses(query_embedding, k) Postgres RPC + TypeScript wrapper.

핵심 결정: 1,000 verse 만 적재된 상태 → 평가셋의 정답 verse 를 Genesis 1~34 안에서만 (정량 10건) + 범위 밖은 사람 판단 (정성 3건).

결과: 정량 100% PASS. cross-lingual (한국어 → 영문 verse) 동작 정량 검증.

6데이터 한 개의 여정

Genesis 1:1 한 구절이 외부 출처에서 검색 가능한 벡터까지 어떻게 변하나.

한 구절이 외부 XML → JSON → DB row (text) → DB row (text+vector) 로 4단계 변환.

7검색은 어떻게 일어나나

한국어 질문이 들어왔을 때 무엇이 어떤 순서로 일어나는지.

한국어 → Gemini 임베딩 → match_verses RPC → cosine 가까운 top-K verse 반환. 모든 게 ~수백 ms 안에 일어남.

중요한 분리 match_verses 함수는 임베딩을 계산하지 않음. 이미 만들어진 query 벡터를 받아서 거리(cosine)만 계산. 임베딩 계산은 TypeScript 쪽이 Gemini API 호출로 처리. 둘이 분리돼있어서 DB 가 외부 API 의존 X.

8자주 헷갈리는 것들

처음 보면 "왜 이렇게?" 싶은 결정들.

왜 Supabase JS 와 pg 직접 연결 둘 다 쓰나?

같은 DB 지만 가는 길이 다름:

  • Supabase JS (PostgREST 경유, HTTP) — 앱 코드용. 브라우저·Vercel 서버·API route 에서 쓸 수 있음. RLS 자동 적용. CRUD·Auth·RPC 호출.
  • pg 직접 연결 (TCP) — 셋업·검증·배치용. 본인 노트북의 스크립트에서만. PostgREST 가 막는 pg_catalog 접근, 대량 INSERT, COPY 등 가능.

예: check:supabase 가 pgvector extension 활성 확인 → 이건 시스템 카탈로그라 PostgREST 로 안 됨 → pg 직접.

왜 임베딩만 1,000 개? 나머지 30k 는?

Gemini 무료 tier 의 embed_content_free_tier_requests = 일일 1,000 requests (RPD). batch API 도 N contents 가 N requests 로 카운트됨 (실측). 그래서 전체 31k 적재 = 무료로는 31일 소요.

학습 페이스로 비현실적이라 1,000 verse 적재로 spec scope 축소 + 잔여는 backlog/queue.md Icebox 에 등록. Tier 1 billing 활성 시 EMBED_BATCH_SIZE=100 EMBED_DELAY_MS=0 pnpm embed:bible 로 분 단위 완료 가능 (비용 ~$0.10 미만).

왜 768 차원? 더 크면 더 정확하지 않나?

Gemini gemini-embedding-001 의 기본은 3072d. 우리는 outputDimensionality:768 옵션으로 768d 로 줄임 (Matryoshka representation — 짧은 차원도 품질 유지).

이유: (1) verses.embedding 컬럼이 spec-01-03 에서 vector(768) 로 정의됐고 (원래 text-embedding-004 기준이었음) (2) Supabase 무료 tier 500MB 안에서 31k row × 768d = ~95MB 안전 (3072d 면 380MB 로 빠듯).

왜 2-pass (text 먼저, embedding 나중)? 한 번에 다 하면 안 되나?

1-pass 도 가능. 단:

  • 중간 실패 시 "어디까지 했지?" 가 흐려짐
  • 외부 progress 파일 필요 (또는 SELECT count 로 추정)

2-pass 는 DB 자체가 진실의 출처. WHERE embedding IS NULL 한 줄로 자동 재개. 매일 RPD 1,000 한도와 자연스럽게 호환 (오늘 1000, 내일 1000, ...).

왜 인덱스 없이 brute force?

현재 1,000 row × 768d cosine 계산 = ~10ms. 인덱스 없이 충분히 빠름. pgvector 인덱스 (ivfflat, hnsw) 는 (1) 빌드 시간 ↑ (2) 메모리 ↑ (3) 정확도 약간 ↓.

전체 31k 적재 후 측정해서 느려지면 그때 인덱스 추가 spec.

RLS ENABLE 인데 정책이 0개면 누가 접근 가능?

Postgres RLS 동작 방식: ENABLE 하면 default 가 deny. 정책 추가하면 그 정책에 부합하는 row 만 select 가능.

그래서 정책 0 + RLS ENABLE = anon/publishable 키로는 0 row 접근 (사실상 차단). secret key 는 RLS bypass 라 무관하게 모든 row 접근 가능.

의도: verses 는 서버 전용 테이블. 사용자가 직접 SELECT 할 일 없음. 검색은 phase-03 의 API route 가 secret key 로 호출.

cosine similarity 점수의 의미가 뭐야?

두 벡터의 방향이 같으면 1, 직각이면 0, 반대면 -1. 우리 SQL 은 1 - (embedding <=> q) 로 계산 → 0~1 직관 친화.

값의미
0.95+거의 동일 (같은 인용)
0.8~0.9paraphrase (같은 의미 다른 표현)
0.6~0.8같은 주제·사건
0.4~0.6관련 있는 주제
<0.4약한 관계

phase-02 에서 "similarity < 0.6 면 답변 거부" 같은 threshold 정책 설계에 직결.

9막혔을 때 — 평소 발생한 함정

phase-01 진행 중 실제로 발생한 사고들. 미래의 너에게.

함정 1 — NEXT_PUBLIC_SUPABASE_URL 끝에 /rest/v1/ Dashboard 의 PostgREST endpoint URL 을 base URL 자리에 그대로 복붙하면 모든 Supabase JS 호출이 "Invalid path specified in request URL" 로 실패. base URL 만 입력 (https://abcd.supabase.co). 끝에 path 안 붙임.
함정 2 — Supabase 의 pgvector schema Supabase 는 pgvector 를 extensions 스키마에 둠. 마이그레이션 SQL 에서 vector(768) 만 쓰면 type lookup 실패. extensions.vector(768) 로 schema-qualified. 함수 안에서 <=> operator 도 같은 이유 → SET search_path = extensions, public 필요.
함정 3 — text-embedding-004 deprecated 2026-01-14 부터 셧다운. 호출하면 404 NOT_FOUND. 신규 모델 = gemini-embedding-001 (기본 3072d). outputDimensionality:768 옵션으로 차원 줄여서 기존 스키마 (vector(768)) 호환 유지.
함정 4 — Gemini 무료 tier RPD 1,000 분 단위 한도가 아니라 일일 1,000 requests. batch API 도 N contents = N requests 카운트 (실측). 한도 도달 시 RESOURCE_EXHAUSTED. embed:bible 스크립트는 graceful exit (exit 0 + "resume tomorrow") 로 처리.
함정 5 — Homebrew git ↔ libcurl 심볼 불일치 macOS Sonoma 에서 brew install supabase/tap/supabase 가 git clone 단계에서 _curl_global_trace 심볼 못 찾아서 실패. 우회: pnpm add -g supabase + 수동 postinstall (node $(pnpm root -g)/supabase/scripts/postinstall.js) + symlink.
함정 6 — pnpm 10 의 build script 차단 pnpm 10 이 보안상 postinstall 등 build script default 차단. supabase 패키지가 postinstall 로 바이너리 다운로드 → 침묵 실패. 수동 실행 우회 가능하지만 인지 필요.
