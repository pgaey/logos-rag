1한 장으로 보는 v1 전체

유저가 어디에 있고, 어디로 요청 가고, 어디서 데이터가 합쳐져서 답이 만들어지는가.

위쪽 = 유저 트래픽이 흐르는 앱 런타임. 아래쪽 = 개발자 노트북에서만 동작하는 스크립트들 (앱과 같은 DB 를 쓰지만 통로가 다름).

3유저 플로우 — 클릭부터 답변까지

유저가 처음 사이트 방문해서 답변을 받기까지 무엇이 일어나는지. v1 완성 시 기준.

v1 완성 시 한 query 의 전체 여정 (5 swim lane · 11 단계). 4가지 외부 서비스 (Vercel · Supabase · Gemini × 2) 가 협력.

주의 — 현재 동작 가능한 부분 위 다이어그램은 v1 완성 후 시점. phase-01 종료 시점 (지금) 은 6·7번 (검색) 까지만 동작. 8번 (LLM) 은 phase-03, 5번 (quota) 은 phase-04 에서 구현 예정. 1~4·9·10·11 (UI/Auth) 도 phase-03.

4데이터 흐름 — 한 query 의 여정

유저가 입력한 한국어 한 문장이 답변이 되기까지 어떤 형태로 변하는지.

Step 1 — USER 한국어 문장 입력

입력 = "하나님이 세상을 만든 이야기 알려줘"

그냥 한국어 텍스트. 영문 성경 DB 와는 아직 어떤 연관도 없음.

Step 2 — GEMINI 임베딩 (의미 → 좌표)

POST gemini.../embedContent
{
  "model": "gemini-embedding-001",
  "contents": ["하나님이 세상을 만든 이야기 알려줘"],
  "config": { "outputDimensionality": 768 }
}

응답 = [0.012, -0.034, 0.51, ..., 0.087]  ← 768개 float

이 벡터는 의미를 압축한 좌표. 비슷한 의미의 영문도 비슷한 좌표를 가짐. 그래서 한국어 → 영문 검색이 가능.

Step 3 — VERCEL Supabase RPC 호출

supabase.rpc('match_verses', {
  query_embedding: '[0.012,-0.034,...,0.087]',
  match_count: 5
})

HTTP → PostgREST → Postgres 의 match_verses 함수로 전달.

Step 4 — POSTGRES cosine 거리 계산

SELECT id, book, chapter, verse, text,
       1 - (embedding <=> $1) AS similarity
FROM verses
WHERE embedding IS NOT NULL
ORDER BY embedding <=> $1
LIMIT 5;

verses 의 모든 row 의 embedding 컬럼과 query 벡터 사이 cosine distance 계산. 가까운 5개 반환.

Step 5 — VERCEL 프롬프트 조립

다음 영문 성경 구절들을 보고 한국어로 답하라:

[Genesis 1:1] In the beginning God created the heavens and the earth.
[Genesis 1:2] Now the earth was formless and empty...
[Genesis 2:1] Thus the heavens and the earth were finished...
...

질문: "하나님이 세상을 만든 이야기 알려줘"

검색된 verse 들을 LLM 에게 컨텍스트로 제공. "이 verse 만 보고 답해" 로 환각 방지.

Step 6 — GEMINI FLASH 답변 생성

응답 = "성경의 첫 권 창세기는 하나님이 천지를 창조하신 것으로 시작합니다.
       Genesis 1:1 은 '태초에 하나님이 천지를 창조하시니라'..."

Flash 가 컨텍스트 + 질문 → 한국어 답변. 답변 안에 영문 근거 verse 인용도 포함.

Step 7 — CLIENT 화면 렌더링

한국어 답변 + 영문 근거 verse 카드 (Genesis 1:1, Genesis 1:2, ...) 를 UI 에 표시. 유저가 verse 카드 클릭하면 원문 표시.

5인증·권한·일일 한도

누구나 무제한으로 쓰면 비용 폭발. 그래서 로그인 + 일일 20회 제한.

인증 (phase-03)

  • Supabase Auth — 이메일/비밀번호 또는 소셜 (구체적 방식은 phase-03 진입 시 결정)
  • 로그인 성공 시 Supabase 가 JWT 발급 → 브라우저 쿠키에 저장
  • 각 API 호출은 이 JWT 를 헤더로 전달. Server 가 auth.users.id 추출
  • 로그인 안 한 상태 = /api/ask 거부

일일 한도 (phase-04)

-- 미래 스키마
CREATE TABLE user_quota (
  user_id    uuid PRIMARY KEY REFERENCES auth.users(id),
  date       date NOT NULL,
  count      int  NOT NULL DEFAULT 0,
  UNIQUE (user_id, date)
);

ALTER TABLE user_quota ENABLE ROW LEVEL SECURITY;
-- 정책: 본인 row 만 SELECT 가능 (사용자가 본인 잔여 확인 UI)

Server 가 /api/ask 호출 시:

  1. JWT 에서 user_id 추출
  2. user_quota 에서 (user_id, today) row 조회
  3. count ≥ 20 이면 HTTP 429 반환
  4. 아니면 count++ 후 검색·LLM 진행
왜 20? 포트폴리오·데모 용도로 적당한 숫자. Gemini Flash 무료 tier RPM·RPD 안에서 여유. 운영하면서 조정 가능 (config 한 줄 변경).

보조 가드 (phase-04)

  • 프롬프트 인젝션 차단 — 입력 길이 제한 + 위험 패턴 (시스템 프롬프트 우회 시도) 필터링
  • 면책 표기 — "이 답변은 AI 생성이며 신학적 권위를 갖지 않습니다" UI 하단 명시
  • IP 기반 보조 제한 (선택) — 멀티 계정 우회 방지

7배포·환경 분리

GitFlow 변형. 어떤 브랜치가 어디로 배포되는지.

브랜치역할배포 대상 (phase-04 이후)
main배포 가능 안정본Vercel Production (실제 URL)
develop통합 브랜치 (phase 단위 누적)Vercel Preview
phase-N-{slug}phase base — spec PR 누적Vercel branch preview (선택)
spec-N-NN-{slug}단일 PR — phase base 로 머지Vercel branch preview (선택)

실제 흐름

spec 작업 → spec branch → PR (base: phase-N) → review → 머지
                                                    ↓
                                phase 의 spec 표 자동 갱신 (sdd)
                                                    ↓
                          모든 spec Merged → /hk-phase-ship
                                                    ↓
                                    phase base → develop PR
                                                    ↓
                                          develop 머지 → Preview 배포
                                                    ↓
                                  (v1 완성 또는 마일스톤 시점)
                                  develop → main PR → Production 배포
왜 phase base branch? spec 마다 main 으로 직접 머지하면 develop 와 무관해짐. phase base 에 spec 들을 누적해서 phase 단위로 통합 테스트 후 develop 로 한 번에 머지. logos-rag 같은 학습 프로젝트에선 다소 무거울 수 있지만 GitFlow 패턴 경험 가치 있음.

8신뢰 경계 — 보안 모델

어떤 키가 어디서 살고, 누가 무엇에 접근 가능한지.

키 / 인증어디에 저장누가 사용권한
sb_publishable_* 브라우저 (NEXT_PUBLIC_ env) 브라우저 JS RLS 정책 따름 (verses 는 0 row)
sb_secret_* Vercel env (서버만) Next.js Server RLS bypass (모든 row)
JWT (유저 세션) 브라우저 쿠키 유저 본인 auth.users 의 본인 row 만
SUPABASE_DB_URL 개발자 노트북 (.env.local) 스크립트 (pg) DB 전체 (superuser-like)
GEMINI_API_KEY Vercel env + 개발자 노트북 Server + 스크립트 Gemini API 호출

핵심 보안 원칙

  • 브라우저는 publishable 만 — secret key 가 클라이언트 번들에 절대 들어가면 안 됨. NEXT_PUBLIC_ prefix 가 강제 (Next.js 가 build 시 분리)
  • verses 는 secret 만 접근 — RLS ENABLE + 정책 0 = anon 접근 자동 차단
  • SUPABASE_DB_URL 은 개발자 노트북만 — Vercel·브라우저 절대 노출 X. Postgres 접속 = 전체 권한이라 노출되면 치명적
  • 키 rotate 가능 — Supabase Dashboard 에서 publishable/secret 각각 rotate. 사고 시 즉시 차단
과거 사고 사례 개발 중 .env.example 에 placeholder 대신 실제 키를 잠시 적어둔 사고 발생. 즉시 발견 + Supabase Dashboard 에서 두 키 모두 rotate. .env.example 은 영원히 placeholder 만 유지하는 게 절대 원칙.

9v1 이후 — v1.5 / v2 / v3

v1 완성 후 가능한 확장 방향.

v1.5 SSO — 앱 분리

현재 v1 은 단일 Next.js 앱. v1.5 에서 분리:

  • 앱 1: 인증 포털 (예: auth.example.com) — Supabase Auth 호스팅
  • 앱 2: RAG 앱 (예: logos.example.com) — 검색·답변
  • 둘 다 같은 Supabase Auth 공유. 한 번 로그인하면 둘 다 인증됨 (쿠키 도메인 공유)

v1 의 src/lib/auth/ 모듈 캡슐화 결정이 이걸 위한 준비.

v2 엔티티 카드

인물 (예: 야곱, 아브라함), 장소 (예: 베델, 예루살렘), 사건 (예: 출애굽) 을 LLM 으로 구조화 추출 → 별도 테이블에 저장 → 답변에 카드 형태로 표시.

-- 예시 스키마
CREATE TABLE entities (
  id        bigserial PRIMARY KEY,
  type      text NOT NULL,  -- 'person' | 'place' | 'event'
  name      text NOT NULL,
  summary   text,
  embedding vector(768)
);

CREATE TABLE entity_verses (
  entity_id bigint REFERENCES entities(id),
  verse_id  bigint REFERENCES verses(id),
  PRIMARY KEY (entity_id, verse_id)
);

v3 관계 그래프

v2 의 entities 사이 관계 (예: 야곱 — 아들 → 요셉) 를 추출하여 그래프 시각화. 라이브러리 미정 (react-flow, vis.js 등 후보).

학습 가치 순서 v1 (RAG 기본) → v1.5 (SSO 패턴) → v2 (LLM 구조화 추출) → v3 (시각화). 각자 다른 기술 학습 = 포트폴리오 두께 ↑.
